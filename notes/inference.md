# 模型推理


## 推理参数


LLM 推理时常见的几个核心参数，理解它们有助于在质量、多样性和速度之间做出正确权衡。

### Maximum New Tokens

**控制模型最多生成多少个 token。**

- 一个 token 大约对应 0.75 个英文单词，或 1～2 个中文字符
- 该参数限制的是输出长度上限，而非强制生成到这个长度
- 模型遇到 `<eos>`（end-of-sequence）token 时会提前停止

**影响：**

| 值 | 效果 |
|---|---|
| 小（如 64） | 输出简短，适合分类、打标签等任务 |
| 大（如 2048+） | 适合长文生成、代码、报告等 |

**注意：** 值越大，推理耗时越长、显存占用越高（KV Cache 随输出长度线性增长）。

---

### Temperature

**控制输出的随机性，本质是对 logits 做缩放。**

采样前，模型对每个 token 的原始得分（logits）除以 Temperature：

```
scaled_logits = logits / temperature
probs = softmax(scaled_logits)
```

| 值 | 效果 |
|---|---|
| `0`（或极小） | 确定性输出，每次都选概率最高的 token（等价于 Greedy Decoding） |
| `0.7` | 较保守，适合代码生成、问答等需要准确性的场景 |
| `1.0` | 使用模型原始概率分布，不做缩放 |
| `> 1.0` | 分布更平坦，随机性更高，适合创意写作，但容易产生无意义输出 |

**直觉：** Temperature 越低，模型越"自信"；越高，模型越"天马行空"。

---

### Top-p (Nucleus Sampling)

**在累积概率达到 p 的最小 token 集合中采样。**

步骤：
1. 将所有 token 按概率从高到低排序
2. 从高到低累加概率，直到累积概率 ≥ p
3. 只在这个"核"（nucleus）内采样

| 值 | 效果 |
|---|---|
| `1.0` | 不过滤，等价于不使用 Top-p |
| `0.9` | 覆盖 90% 概率质量，过滤掉长尾低概率 token |
| `0.5` | 更保守，只在高概率 token 中选择 |

**与 Top-k 的区别：** Top-k 固定选前 k 个 token，Top-p 根据概率分布动态决定候选数量，更自适应。

**Temperature 与 Top-p 同时使用时：** 一般先用 Temperature 缩放 logits，再用 Top-p 过滤候选集，最后采样。实践中通常只调其中一个，另一个保持默认（`temperature=1.0` 或 `top_p=1.0`）。

---

### Top-k

**只从概率最高的 k 个 token 中采样。**

步骤：
1. 将所有 token 按概率从高到低排序
2. 只保留前 k 个
3. 在这 k 个 token 中重新归一化概率后采样

| 值 | 效果 |
|---|---|
| `1` | 等价于 Greedy Decoding，每次选概率最高的 token |
| `50` | 常用默认值，平衡多样性与质量 |
| 极大（如 10000+） | 接近不过滤，等价于不使用 Top-k |

**与 Top-p 的对比：**

| | Top-k | Top-p |
|---|---|---|
| 候选数量 | 固定为 k 个 | 动态，取决于概率分布 |
| 分布平坦时 | 可能包含太多低质量 token | 自动缩小候选集 |
| 分布尖锐时 | 可能排除掉合理候选 | 自动扩大候选集 |

实践中 Top-p 比 Top-k 更常用，但两者可以叠加使用（先 Top-k 过滤，再 Top-p 过滤）。

## 推理引擎

常见的 LLM 推理引擎各有侧重，选型时主要看场景是本地体验、研究实验还是生产服务。

### Ollama

面向本地部署的一键式推理工具，封装了模型下载、量化和服务启动。

- 安装极简，`ollama run llama3` 即可跑起来
- 自带模型仓库，支持 GGUF 格式量化模型，CPU 也能跑
- 提供 OpenAI 兼容 API，方便接入现有工具链
- **局限：** 性能优化有限，不适合高并发生产场景

### HuggingFace Transformers

学术界和研究领域的事实标准，模型生态最全。

- 支持几乎所有主流模型架构，模型切换成本极低
- 与训练、微调（PEFT、SFT）流程无缝衔接
- 文档完善，社区活跃
- **局限：** 原生推理性能一般，吞吐量不高，需要配合 `accelerate` 等库才能发挥多卡潜力

### vLLM

专为生产级高吞吐推理设计，核心创新是 PagedAttention。

- PagedAttention 大幅提升 KV Cache 利用率，吞吐量远超原生 Transformers
- 支持连续批处理（Continuous Batching），并发请求下延迟稳定
- OpenAI 兼容 API，部署即可替换 OpenAI 接口
- **局限：** 启动较重，本地轻量使用略显繁琐；对非主流模型架构支持滞后

### SGLang

专注于复杂推理场景（多轮对话、Agent、结构化输出）的高性能推理框架。

- RadixAttention 机制让共享前缀的请求复用 KV Cache，多轮场景下效率显著更高
- 原生支持结构化输出（JSON Schema）和推理时计算（chain-of-thought）
- 吞吐量与 vLLM 相当，部分场景（长上下文、多轮）更优
- **局限：** 生态相对年轻，模型兼容性和社区资源不及 vLLM

### 横向对比

| | Ollama | HuggingFace | vLLM | SGLang |
|---|---|---|---|---|
| 上手难度 | 极低 | 低 | 中 | 中 |
| 推理吞吐 | 低 | 低～中 | 高 | 高 |
| 生产可用性 | 否 | 有限 | 是 | 是 |
| 多轮 / Agent 优化 | 否 | 否 | 一般 | 强 |
| 模型生态 | 中（GGUF） | 最全 | 主流模型 | 主流模型 |
| 适用场景 | 本地体验 | 研究 / 微调 | 生产 API 服务 | 复杂推理 / Agent |
